上下文是什么？token 怎么计费？

2026-11-19 • AI 学习路线

之前的两篇文章（Token 到文本生成、Transformer 一次生成流程）讲的是模型怎么生成下一个 token。这篇讲另一个决定性的东西：模型每次请求能"看见"什么，以及这一切怎么算钱。

上下文 = 每轮都全量重发的对话历史

模型没有记忆。你在聊天框里打第三句话时，API 实际收到的是完整历史：

[system 系统提示] [用户第1句] [助手回复] [用户第2句] [助手回复] [用户第3句]  ← 本次全部发送

上下文窗口（context window）就是这个列表能装下的最大 token 数。当前主流模型是 200K 上下文，听起来很大，但实际算笔账：一个中型代码库的几个文件 + 几十轮对话 + 工具返回的日志，很快就会逼近上限。

两个直接后果：

  1. 每轮的输入成本随对话轮数线性增长，长会话越到后面每句话越贵；
  2. **装不下的内容就是"不存在"**——超长对话开头的内容会被截断或压缩，模型会一本正经地"忘记"你最初的要求。

所以 Agent 工程的几乎所有技巧——压缩历史、子代理隔离、按需加载文档——本质都是上下文管理。

计费结构：三种 token 单价不同

API 按 token 计费，但不是所有 token 一个价：

类别 说明 相对价格
输入（input） 你发给模型的全部内容 基准价
输出（output） 模型生成的回复 通常是输入的 4~5 倍
缓存写入（cache write） 首次缓存稳定的前缀 输入价的约 1.25 倍
缓存读取（cache read） 命中缓存的前缀 输入价的约 10%

输出贵是因为生成比读取慢、计算量在每一步都要做完整的下一词预测。最值得注意的是提示缓存（prompt caching）：前缀完全一致时，第二次请求只需为缓存读取付约 10% 的输入价。

这就是为什么 API 的最佳实践永远是：系统提示和工具定义放最前面且保持稳定，变化的内容放最后。乱序的对话历史会打碎缓存前缀，每轮都全价重算。Agent 工具（如 Claude Code）自动做了这件事，自己拼 messages 时要自己做。

一个真实的成本直觉

假设输入 $3/百万 token、输出 $15/百万 token：

一轮对话历史累计 40K input + 本次生成 2K output：
输入成本 ≈ 40K/1M × $3 = $0.12
输出成本 ≈ 2K/1M × $15 = $0.03

第 20 轮时历史涨到 200K：
输入成本 ≈ $0.60 —— 单轮是第一轮的 5 倍

不带缓存跑长会话，成本曲线会陡到你怀疑人生。而缓存命中时，那 200K 里大部分按 10% 计价。

省钱的工程手段

按效果排序：

  1. 及时清场：换任务就清上下文，别让上一个任务的残留陪你聊完下一个任务；
  2. 压缩历史：接近上限时用摘要替代原文（Claude Code 的 /compact），保留结论丢弃过程；
  3. 裁剪工具结果：让工具返回"结论"而不是全量数据——读文件返回相关段落、查日志返回统计值，而不是整个文件整个日志；
  4. 子代理隔离：大量中间输出放到子代理的独立窗口里，主对话只接收结论；
  5. 稳定前缀：自己调 API 时把不变的内容放前面，最大化缓存命中。

感受一下 200K token

  • 约等于 15 万汉字，一部中篇小说；
  • 一个 100KB 的源代码文件大约 25K token——八个文件就能塞满；
  • 一张按主流 tokenizer 编码的截图可能上千 token——多模态输入同样计费。

这也解释了为什么"把整个代码库塞给模型"不可行，以及为什么检索和按需加载不是优化项而是必需品。
