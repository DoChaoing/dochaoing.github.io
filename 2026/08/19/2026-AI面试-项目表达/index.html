AI 项目面试怎么讲：用问题、取舍和证据替代框架清单

2026-08-19 • AI 面试

“项目用了 LangChain、向量数据库和大模型 API”不是项目介绍，只是一份依赖清单。面试官真正想确认的是：你解决了什么问题，为什么这样设计，如何证明它有效，以及失败时你做了什么。

用六段结构组织答案

问题与约束
  -> 我的职责
  -> 方案与取舍
  -> 最难的问题
  -> 验证结果
  -> 失败与改进

控制第一轮介绍在两到三分钟。每一段只留下一个可继续追问的重点。

1. 问题与约束

不要从“我做了一个 RAG”开始。说明谁在什么场景遇到了什么困难，以及限制条件。

例如：内部文档分散，客服需要快速找到政策依据；数据不能发送到外部服务；答案必须显示来源；高峰期有固定并发要求。

2. 明确你的职责

团队项目中，要区分“团队实现”和“我负责”。可以说自己负责文档解析、检索评测和 API 服务，而前端由同事完成。夸大职责很容易在深入追问时暴露。

3. 解释技术取舍

使用一个方案时同时说出被放弃的方案：

  • 为什么先用 dense retrieval，而不是直接上混合检索；
  • 为什么选小模型，而不是参数更大的模型；
  • 为什么同步接口足够，暂时没有引入消息队列；
  • 为什么使用 Schema 约束，而不是解析自由文本。

好的取舍必须联系业务约束，而不是“网上都这么用”。

4. 讲一个真正困难的问题

选你亲自定位过的问题，例如长表格被错误切分导致检索失败。按照“现象—假设—实验—结论—修复”回答。

不要把“安装依赖很麻烦”当成核心技术难点，除非你能解释具体兼容问题和解决机制。

5. 用证据描述结果

结果可以是 Recall@5、结构校验通过率、P95 延迟、错误率或人工评测一致率。必须说明测试集、环境和对照方案。

“准确率提升 30%”如果没有指标定义、样本数量和基线，信息价值很低。

6. 主动讲失败和边界

指出系统在哪些查询上仍会失败，以及下一步优先解决什么。能够清楚描述边界，通常比声称“效果很好”更可信。

高频追问清单

  • 不使用这个框架能否实现？
  • 数据更新后如何重建索引？
  • 如何避免模型泄露敏感信息？
  • 为什么选择这个 Embedding 或模型？
  • 指标下降时先查哪一层？
  • 如果并发扩大十倍，瓶颈在哪里？

面试前准备材料

准备一张架构图、一条完整请求链路、三项真实指标、两个失败案例和一个可以展示的代码片段。不要临场回忆所有细节。

项目表达的核心是证明你具备工程判断，而不是证明你安装过很多工具。
