Mac 本地部署大模型：从 Ollama 安装到性能调优

2026-08-28 • AI 应用实战

Mac 的 CPU 和 GPU 共享统一内存，因此很适合在个人电脑上学习大模型部署：不需要安装 CUDA，也能使用 Apple GPU 加速推理。但“模型可以启动”和“模型运行得好”是两回事。

本文使用 Ollama 作为部署主线。它安装简单、提供本地 API，并在 Apple 芯片上内置 Metal 支持。最后再介绍什么时候值得换用 Apple 的 MLX LM。

本文讨论的是本地推理优化，不是训练基础大模型。下载前应检查模型许可证和磁盘空间。

一、确认 Mac 能跑多大的模型

先查看芯片、统一内存和系统版本：

system_profiler SPHardwareDataType
sw_vers

Ollama 当前要求 macOS 14 或更新版本。Apple M 系列支持 CPU 和 GPU，Intel Mac 只能使用 CPU，后者不适合运行较大的模型。

Mac 上最重要的不是“显存是多少”，而是统一内存有多少。模型权重、KV Cache、系统和其他应用共享这块内存。可用下面的经验值做第一轮选择：

统一内存 建议起步 适合任务
8 GB 1B～3B 的 4-bit 模型 摘要、改写、简单问答
16 GB 3B～8B 的 4-bit 模型 中文问答、轻量代码辅助
24～32 GB 7B～14B 的 4-bit 模型 RAG、代码和复杂推理
48 GB 以上 更大模型或更长上下文 本地实验、低并发服务

这不是硬性边界。同为 8B 模型，量化格式、上下文和并发不同，内存占用也不同。务必给 macOS 留出余量；出现明显卡顿或大量交换空间时，应该换小模型。

二、安装 Ollama

从 Ollama 官网 下载 DMG，将应用拖入“应用程序”后启动。首次运行会检查终端中的 ollama 命令。

ollama --version
ollama list
df -h /

模型可能占用数 GB 到数十 GB，默认数据位于 ~/.ollama，所以下载前要检查磁盘空间。

三、完整实验：安装 Qwen3.5 4B

下面不再使用占位符，直接用 qwen3.5:4b 完成一次实验。它体积较小、支持中文，适合 Apple 芯片 Mac 入门。如果当前 Ollama 版本不能识别它，请先升级 Ollama；也可以把全文模型名替换为 qwen3:4b。

第 1 步：确认 Ollama 服务正常

打开 Ollama 应用，然后在终端执行：

curl http://127.0.0.1:11434/api/tags

看到 JSON 说明服务已经启动。若连接失败，先确认菜单栏里有 Ollama 图标，或者手动运行：

ollama serve

如果提示端口已经被占用，通常表示应用版服务已经在运行，不需要再启动一个。

第 2 步：下载模型

ollama pull qwen3.5:4b

下载完成后确认模型存在：

ollama list
ollama show qwen3.5:4b

show 的结果会包含模型家族、参数规模、量化信息和上下文能力。模型库中的具体文件可能随发布更新，因此不要在文章里假定固定文件大小。

第 3 步：在终端完成第一次对话

ollama run qwen3.5:4b

依次输入下面三个问题：

你是谁？请用一句中文回答。

把“本地模型不会把请求发送给远程 API”改写成更严谨的说法。

写一个 Python 函数，输入字符串列表，返回长度最长的字符串，并给出两个测试用例。

这一轮分别检查中文能力、事实表达和代码能力。不要只问“你好”，那无法判断模型是否适合实际任务。输入 /bye 结束对话。

第 4 步：检查是否使用 GPU

让模型保持加载状态，然后另开一个终端：

ollama ps

重点看三列：

  • PROCESSOR：是否为 100% GPU；
  • CONTEXT：实际分配的上下文长度；
  • UNTIL：模型还会在内存中保留多久。

如果主要在 CPU 上运行，先关闭占用内存较大的应用，再降低上下文；仍然无法完全放入 GPU 时，换成 qwen3.5:2b：

ollama pull qwen3.5:2b
ollama run qwen3.5:2b

四、把本地模型变成一个摘要工具

终端聊天只是验证模型能运行。接下来做一个真正可用的小程序：输入一段技术笔记，让本地模型返回标题、摘要和关键词。

第 1 步：创建 Python 环境

mkdir ollama-mac-demo
cd ollama-mac-demo
python3 -m venv .venv
source .venv/bin/activate
pip install ollama

创建 app.py：

import json
from ollama import chat

article = """
KV Cache 保存大模型生成过程中已经计算过的 Key 和 Value。
这样模型生成下一个 Token 时，不必重新计算全部历史内容。
它能减少重复计算，但占用会随着上下文长度和并发量增加。
"""

response = chat(
    model="qwen3.5:4b",
    messages=[
        {
            "role": "system",
            "content": (
                "你是技术编辑。只能依据用户提供的原文回答，"
                "不得补充原文不存在的事实。"
            ),
        },
        {
            "role": "user",
            "content": f"""请整理下面的笔记：

{article}

返回 JSON，字段为 title、summary、keywords。
keywords 必须是 3 个中文字符串组成的数组。""",
        },
    ],
    format={
        "type": "object",
        "properties": {
            "title": {"type": "string"},
            "summary": {"type": "string"},
            "keywords": {
                "type": "array",
                "items": {"type": "string"},
                "minItems": 3,
                "maxItems": 3,
            },
        },
        "required": ["title", "summary", "keywords"],
    },
    options={
        "temperature": 0,
        "num_ctx": 4096,
        "seed": 42,
    },
)

result = json.loads(response.message.content)
print(json.dumps(result, ensure_ascii=False, indent=2))

运行：

python app.py

预期看到类似结构，而不是要求字句完全一致：

{
  "title": "KV Cache 的作用与代价",
  "summary": "KV Cache 通过保存已计算的 Key 和 Value 减少重复计算，但会随上下文和并发增长而占用更多内存。",
  "keywords": ["KV Cache", "重复计算", "内存占用"]
}

如果能够稳定解析 JSON，这个最小应用才算通过。实际项目还需要捕获连接失败、超时、空输出和 JSON 解析错误。

五、实际跑一次性能基线

先用 API 做一次非流式测试。非流式响应会返回完整性能指标：

curl http://127.0.0.1:11434/api/generate -d '{
  "model": "qwen3.5:4b",
  "prompt": "用三点解释什么是 KV Cache，每点不超过 30 字。",
  "stream": false,
  "keep_alive": "10m",
  "options": {
    "temperature": 0,
    "num_predict": 128,
    "num_ctx": 4096,
    "seed": 42
  }
}'

响应末尾包含：

  • load_duration：模型加载耗时；
  • prompt_eval_count / prompt_eval_duration：输入处理量和耗时；
  • eval_count / eval_duration：输出生成量和耗时；
  • total_duration：整个请求耗时。

输出速度的计算方式是：

输出 tokens/s = eval_count ÷ (eval_duration ÷ 1,000,000,000)

首次调用包含冷启动成本。keep_alive 让模型暂时留在内存中，便于继续测预热后的速度。

自动比较 2K 与 8K 上下文

创建 benchmark.py：

import statistics
import time
import ollama

MODEL = "qwen3.5:4b"
PROMPT = "用三点解释什么是 KV Cache，每点不超过 30 字。"


def run_once(num_ctx: int) -> dict:
    started = time.perf_counter()
    result = ollama.generate(
        model=MODEL,
        prompt=PROMPT,
        stream=False,
        keep_alive="10m",
        options={
            "temperature": 0,
            "seed": 42,
            "num_predict": 128,
            "num_ctx": num_ctx,
        },
    )
    elapsed = time.perf_counter() - started
    output_tps = result["eval_count"] / (result["eval_duration"] / 1e9)
    return {"seconds": elapsed, "output_tps": output_tps}


for context in (2048, 8192):
    run_once(context)  # 预热，不计入结果
    rows = [run_once(context) for _ in range(5)]
    print(
        f"ctx={context:<5} "
        f"平均总耗时={statistics.mean(r['seconds'] for r in rows):.2f}s "
        f"平均输出速度={statistics.mean(r['output_tps'] for r in rows):.2f} tok/s"
    )
python benchmark.py

不要在文章里伪造一组“标准成绩”。芯片、内存带宽、温度、后台程序和 Ollama 版本都会影响结果。读者应该把自己实际输出的两行数据保存下来，并回答：

  1. 8K 上下文是否明显增加内存压力？
  2. 这个任务实际上是否需要 8K？
  3. 两种配置的答案质量是否一致？
  4. 活动监视器是否出现黄色或红色内存压力？

如果短摘要任务在 2K 下已经完成，8K 没有带来质量提升，那么 2K 就是更合理的设置。这就是一次最小的、有数据支撑的调优，而不是凭感觉修改参数。

六、建立一份公平的测试基线

准备 10～30 个固定问题，覆盖真实需求：中文摘要、JSON 抽取、代码解释、基于资料回答、生成可执行单元测试等。

比较模型或参数时固定 Prompt、seed、温度、上下文和最大输出长度，并记录：

指标 回答的问题
任务成功率 回答是否真的可用
首次/预热后总耗时 慢在加载还是推理
输入 tokens/s 长文档处理是否够快
输出 tokens/s 回答生成是否流畅
内存压力 是否影响整台 Mac

同时打开“活动监视器”的“内存”窗口，关注内存压力和交换使用量。速度不错但系统持续变黄、变红，不是稳定配置。

七、Mac 上最有效的五个调优方向

1. 先换合适的模型大小

模型大小通常比微调参数更影响速度和内存。如果 14B 只能勉强运行，换成优秀的 7B/8B 往往更流畅。

采用“两阶段选择法”：先用固定题集淘汰质量不达标的模型，再在合格模型中选择速度最快、内存最稳的一个。参数更多不等于你的任务一定更好，摘要、分类和格式抽取常常不需要大模型。

2. 比较量化，而不是只追求最低位数

Ollama 模型通常使用 GGUF 量化。4-bit 能显著降低权重占用，适合作为 Mac 的起点；但量化越激进，质量下降风险越高。

比较量化版本时保持题集和生成参数一致，观察输出速度、内存压力，以及代码、JSON、中文和长文本质量。如果 4-bit 已经完全驻留 GPU，继续压低位数未必值得。

3. 控制上下文长度

上下文越长，KV Cache 占用越大。普通问答先用 4096 或 8192，不要直接打开最大窗口。API 中可按请求设置：

{
  "options": { "num_ctx": 4096 }
}

也可以新建 Modelfile 固化配置：

FROM <模型名>
PARAMETER num_ctx 4096
PARAMETER temperature 0.2
PARAMETER num_predict 512
ollama create mac-ai-balanced -f Modelfile
ollama run mac-ai-balanced

RAG 不要把整个资料库塞进上下文。先检索，再只放最相关片段，通常比盲目增加窗口更快、更准确。

4. 限制并发和已加载模型

个人 Mac 更适合单用户或低并发服务。并行请求会增加上下文所需内存；并发和上下文同时扩大，很容易造成内存压力。

关闭 Ollama 应用内的服务后，可以用保守配置启动：

OLLAMA_NUM_PARALLEL=1 \
OLLAMA_MAX_LOADED_MODELS=1 \
OLLAMA_MAX_QUEUE=32 \
OLLAMA_CONTEXT_LENGTH=4096 \
ollama serve

确认单并发稳定后，再尝试把 OLLAMA_NUM_PARALLEL 调到 2。每次只改一个参数并重复压测。Mac 不适合作为裸露公网的高并发服务器，公网服务仍需要鉴权、TLS、限流和监控。

5. 优化输入和输出长度

最便宜的优化往往在请求本身：

  • 删除重复系统提示词和无关历史；
  • RAG 文档先去重、切分和重排；
  • 明确要求回答长度；
  • 设置合理的 num_predict；
  • 摘要和分类使用低温度；
  • 结构化任务提供明确字段或 JSON Schema。

输入越长，等待首字通常越久；输出越长，占用设备的时间也越长。

八、一张可复现的调优实验表

一次只改变一个主要变量：

实验 模型 量化 上下文 并发 目的
A 3B 4-bit 4096 1 最小速度基线
B 8B 4-bit 4096 1 比较质量收益
C 8B 4-bit 8192 1 测试长上下文成本
D 8B 4-bit 4096 2 测试并发与内存
E 最优模型 另一量化 4096 1 比较量化质量

最终选择不应该是单项冠军，而是同时满足：

质量达标 + 内存压力稳定 + 生成速度可接受 + 不影响日常工作

九、什么时候使用 MLX LM

如果只是聊天、RAG 或给程序提供本地 API，Ollama 已经足够方便。如果想深入 Apple 芯片模型开发、自己量化或进行 LoRA 微调，可以尝试 Apple 开源的 MLX LM：

python3 -m venv .venv
source .venv/bin/activate
pip install mlx-lm

mlx_lm.generate \
  --model mlx-community/Llama-3.2-3B-Instruct-4bit \
  --prompt "解释统一内存为什么适合本地大模型"

MLX LM 可以加载 Hugging Face 上的 MLX 模型，也支持量化、低秩微调、KV Cache 量化和推测解码。它更偏实验与开发，具体参数应以当前版本的命令帮助和官方文档为准。

十、常见问题

模型一运行，整台电脑就卡

说明统一内存余量不足。关闭高内存应用，降低上下文，确保只加载一个模型；仍不稳定就换更小模型或更高压缩率的量化版本。

第一次回答特别慢

先查看 load_duration。模型从磁盘载入内存会产生冷启动时间，预热后的请求才适合衡量推理速度。

同一个问题每次结果差很多

降低 temperature 并固定 seed。性能和质量对比时要减少随机性。

模型支持 128K，为什么不直接启用

最大能力不等于免费能力。更大的上下文增加内存占用和输入处理时间，应按真实任务设置。

能不能让同一 Wi-Fi 下的设备访问

技术上可以修改监听地址，但这会扩大安全边界。至少应通过带认证和 TLS 的代理访问，并设置防火墙、限流和输入长度限制；不要把裸 Ollama 端口映射到公网。

总结

在 Mac 上部署和调优大模型，可以遵循这条路线：

确认统一内存 → 安装 Ollama → 选择小模型建立基线
→ 检查 GPU 驻留 → 比较模型与量化 → 控制上下文和并发
→ 用真实题集验证质量 → 固化稳定配置

Mac 调优最重要的原则不是把模型做得尽可能大，而是让模型、上下文和并发共同适配统一内存。保留可复现的题集和数据，才能让每次优化成为清晰的工程决策。
