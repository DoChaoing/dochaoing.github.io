AI 系统设计面试：如何设计一个可上线的知识库问答服务

2026-08-23 • AI 面试

AI 系统设计面试不是画出“用户—大模型—数据库”三个框。一个可上线方案需要同时处理数据更新、权限、质量、延迟、成本和故障。

第一步：澄清需求

先问：用户是谁、文档规模、更新频率、并发量、延迟目标、是否需要引用、是否允许外部模型、数据权限和不可接受的错误。

没有这些信息，就无法判断是否需要向量库、队列、缓存或本地部署。

第二步：拆分离线与在线链路

离线：文档接入、解析、清洗、切分、Embedding、索引、版本和权限元数据。

在线：认证、问题处理、权限过滤、检索、重排、上下文构造、模型生成、引用校验和日志。

分开后可以独立扩缩容，也更容易定位数据问题还是请求问题。

第三步：权限必须进入检索

不能先检索所有文档，再只在界面隐藏无权限结果。权限或租户字段应参与过滤，缓存键也必须包含用户权限范围，避免跨用户泄露。

模型上下文和日志同样需要数据最小化。

第四步：设计降级路径

  • 向量库不可用：返回暂时不可查询，而不是让模型自由回答；
  • Reranker 超时：降级到基础检索；
  • 生成模型超时：返回已找到的相关文档；
  • 没有高分证据：明确提示资料不足；
  • 文档更新失败：保留上一版可用索引并告警。

降级结果必须让用户知道能力发生变化。

第五步：缓存哪些内容

可以缓存 Embedding、稳定查询的检索结果、公共前缀和非敏感生成结果。缓存前先定义失效条件：文档版本、模型版本、Prompt 版本和权限范围变化都可能使缓存过期。

第六步：如何扩展

无状态 API 可以水平扩容；模型服务按 GPU 资源与批处理能力扩容；文档处理通过任务队列异步执行；向量库根据数据量、查询量和可用性要求分片或复制。

不要一开始就设计成几十个服务。先识别真正需要独立扩展或隔离故障的部分。

第七步：质量和运行指标

离线评测包括 Recall@k、引用正确性、答案正确性与拒答。线上关注 TTFT、P95 延迟、错误率、无答案率、每请求 token、工具或检索失败率和用户反馈。

索引、Embedding、Prompt 或模型变化时重新运行固定评测集。

安全问题

把文档内容视为不可信输入，防止其中的指令覆盖系统规则；限制工具权限；对输出做内容和数据泄露检查；日志与评测样本进行脱敏和访问控制。

最终架构描述

用户 -> API / 鉴权 -> 检索编排
                    -> 权限过滤 -> 混合检索 -> 重排
                    -> 上下文构造 -> 模型服务
                    -> 引用与响应

文档 -> 解析 / 切分 -> Embedding -> 带版本和权限的索引

面试回答最后应主动说明容量假设、单点故障、成本最大的环节和下一阶段优化，而不是停在架构图。
