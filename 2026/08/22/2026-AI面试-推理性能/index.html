大模型推理面试：首 Token 延迟、吞吐量和 KV Cache

2026-08-22 • AI 面试

“这个模型每秒能生成多少 token”不能完整描述推理服务。交互体验、系统容量和硬件成本需要不同指标。

TTFT：首 Token 延迟

Time to First Token 从请求进入到收到第一个输出 token。它受排队、Prompt 长度、Prefill、模型大小和调度影响。长文档请求通常比短问题有更高 TTFT。

TPOT 与生成速度

Time per Output Token 衡量 decode 阶段相邻输出 token 的时间。也常用每秒输出 token 表示。它更直接影响流式回答开始后的速度。

不要把输入 token 和输出 token 混在同一个吞吐量数字里。

吞吐量与延迟的取舍

动态批处理可以让 GPU 同时服务多个请求，提高总吞吐量，但请求等待和竞争也可能增加单请求延迟。面试中应说明目标是交互式聊天、离线批处理还是高并发 API。

KV Cache 为什么占显存

自回归生成会重复使用历史 token 的 Key 和 Value。缓存它们避免每一步重算，但占用随层数、序列长度、并发和缓存精度增加。

因此长上下文和高并发会竞争同一块显存。模型权重能加载，不代表服务能承受目标并发。

量化解决什么

量化使用更低精度表示权重或激活，主要价值是降低内存和计算成本。Hugging Face 当前 Transformers 支持 bitsandbytes 的 8-bit/4-bit，以及 AWQ、GPTQ 等方案。

量化不保证所有硬件上都更快。需要测试质量、首 token 延迟、生成速度和峰值内存。

如何设计压测

固定模型、量化、硬件和采样参数，构造不同输入/输出长度与并发组合。至少报告：

  • TTFT 的 P50、P95；
  • TPOT 或输出 token/s；
  • 请求吞吐量；
  • 错误率与超时率；
  • GPU 利用率和峰值显存；
  • 输入与输出长度分布。

先预热模型，再运行足够时间。只测一次短请求不能代表线上能力。

常见优化方向

  • Continuous batching：动态组合正在运行的请求；
  • Paged KV Cache：更灵活地管理缓存内存；
  • Quantization：降低权重或缓存占用；
  • Prefix caching：复用相同前缀；
  • Speculative decoding：使用草稿模型减少主模型解码步骤；
  • Tensor parallel：跨多卡切分模型。

每项优化都有适用条件，应通过真实负载验证，而不是全部开启。

面试回答结构

先区分 Prefill 和 Decode，再分别解释 TTFT 与 TPOT，接着说明并发/批处理的吞吐量取舍，最后给出压测设计和瓶颈定位方法。
